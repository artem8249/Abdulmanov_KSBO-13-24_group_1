## 2. Постановка задачи и контекст

Опишите:

1. **Предметную область и задачу:**
   - Рекомендательная система;
   - Покупатель интернет-магазина одежды. Сценарий: при заходе на главную страницу или в корзину сервис мгновенно формирует для него персонализированную ленту товаров.

2. **Формулировку задачи в терминах ML/ИИ:**
   - Для «теплых» пользователей — история покупок(id пользователя); для «холодных» — демография (возраст, подписки).
   - Финальный выход системы — отсортированный список из Top-K ID товаров;
   - Жесткие требования к скорости ответа (latency). Из-за этого запрещен тяжелый инференс по всей базе: сначала FAISS делает быстрый отбор 150 кандидатов, и только их ранжирует LightGBM.

3. **Целевые метрики качества:**
   - Используемые метрики: ROC-AUC для ML-модели, а также Precision@20 и Recall@20 для финальной бизнес-выдачи;
   - ROC-AUC используется для оптимизации градиентного бустинга, так как отлично оценивает способность модели ранжировать классы (покупка / не покупка) при их сильном дисбалансе.Precision@K и Recall@K оценивают качество итогового сервиса: Precision показывает, какая доля из предложенных K товаров была реально куплена, а Recall — какую долю из всех целевых покупок пользователя наша система смогла «поймать» и показать в топ-K..

## 3. Данные

Опишите, какие данные использует проект:

1. **Источник данных:**
   - Набор данных: В проекте используется открытый датасет соревнований Kaggle — H&M Personalized Fashion Recommendations(https://www.kaggle.com/competitions/h-and-m-personalized-fashion-recommendations/data)

2. **Структура данных:**
   -Таблица товаров (`articles.csv`):
     - Ключевые признаки: `article_id` (уникальный ID), текстовое описание `detail_desc`.
     - Типы данных: Категориальные (группы товаров, отделы, цвета) и текстовые (описания).
   - Таблица пользователей (`customers.csv`):
     - Ключевые признаки: `customer_id` (уникальный хэш), `age` (возраст), `fashion_news_frequency` (статус подписки на рассылку).
     - Типы данных: Категориальные и числовые.
   - Таблица транзакций (`transactions_train.csv`):
     - Ключевые признаки: `t_dat` (дата покупки), `customer_id`, `article_id`, `price` (цена на момент транзакции).
     - Типы данных: Временные (DateTime), строковые ID и числовые (цена с плавающей точкой).

3. **Предобработка и EDA:**
   Основные шаги предобработки:
      - Хронологический сплит (Time-based split): Данные разделены на обучающую, валидационную и тестовую выборки строго по времени (`t_dat`), чтобы избежать "заглядывания в будущее" (data leakage).
      - Фильтрация жизненного цикла: Исключены неактуальные (архивные) товары на основе дат их последней продажи. Для рекомендаций оставлены только товары со статусом _Active_ и _New_.
      - Feature Engineering: На основе транзакций рассчитаны новые признаки для товаров: медианная цена (`price`) и количество продаж (`popularity`). Возраст покупателей разбит на дискретные интервалы (`age_group` от "16-24" до "50+").
      - Обработка текста: Пропуски в текстовых описаниях (`detail_desc`) заполнены заглушками, после чего тексты преобразованы в плотные векторные представления (эмбеддинги) с помощью предобученной языковой модели BERT для использования в FAISS-индексе.
      - Negative Sampling (Сэмплирование): Для обучения ранжирующей модели бинарной классификации факты реальных покупок размечены как класс 1. В качестве класса 0 отобраны некупленные товары-кандидаты из выдачи FAISS (в соотношении 1:5 к позитивным примерам), чтобы избежать сильного дисбаланса.

   Важные наблюдения из анализа данных (EDA):
      - Проблема «Холодного старта»: Значительная доля покупателей совершает лишь одну-две покупки. Из-за недостатка истории (user history) для таких пользователей была внедрена fallback-логика (выдача популярных товаров на основе демографических когорт).
      - Long Tail (Длинный хвост): Ярко выраженная несбалансированность популярности — малая часть ассортимента (бестселлеры) генерирует подавляющее большинство продаж, в то время как большинство товаров покупаются редко.
      - Пропуски: Множество пользователей не указали статус подписки или возраст (пропуски успешно обработаны заменой на моду: NONE и 25-34 соответственно).

## 4. Модели и подходы

Опишите, какие модели вы пробовали и как развивался ваш подход:

1. **Базовые (baseline) модели:**
   - Подходы: В качестве отправной точки (exp02_baseline.ipynb) были реализованы неперсонализированные эвристики: выдача глобальных хитов продаж (Global Popularity) и популярных товаров внутри возрастных когорт (Age-based Popularity).

   - Результаты: Эти модели зафиксировали базовый уровень метрик Precision@20 и Recall@20. При этом подход Age-based отлично показал себя и был оставлен в финальной системе как fallback-решение для пользователей без истории покупок (холодный старт).

2. **Улучшенные модели и эксперименты:**
   - Архитектуры: Выполнен переход к персонализированному ранжированию как задаче бинарной классификации. В exp03_Random_forest&Boosting.ipynb протестированы Random Forest и HistGradientBoosting. Финальный выбор (exp05_BERT_and_LGBM.ipynb) — двухуровневая система, где кандидатов ранжирует LightGBM.

   - Эксперименты: Ключевым нововведением стал векторный отбор кандидатов и внедрение Negative Sampling (генерация некупленных товаров в качестве класса 0) для обучения бустинга.

   - Гиперпараметры: С помощью фреймворка Optuna был автоматизирован подбор параметров. Наибольшее влияние на прирост ROC-AUC оказали параметры learning_rate, max_depth (глубина деревьев) и num_boost_round (количество итераций). Подбор проводился строго с изоляцией тестовой выборки.
3. **Нейросетевые модели (если применимо):**
   - Архитектура: Для обработки текстов применялась трансформерная модель семейства BERT на базе PyTorch и HuggingFace, реализованная в exp04_BERT.ipynb.

   - Особенности: Модель не дообучалась с нуля, а использовалась для извлечения признаков — перевода текстовых описаний товаров в семантические векторы (эмбеддинги). Инференс выполнялся батчами с поддержкой GPU/MPS.

   - Интеграция: Полученные эмбеддинги были загружены в векторный индекс FAISS. Это позволило системе находить скрытые связи между товарами по их описанию и эффективно рекомендовать нишевые товары из длинного хвоста, у которых слишком мало продаж для классических ML-моделей.Финальный выбор (exp05_BERT_and_LGBM.ipynb) — двухуровневая система, где собирает топ 100 кандидатов BERT.

## 6. Архитектура решения и сервис

### 6.1. Архитектура пайплайна

Решение построено по **двухэтапной схеме рекомендаций (retrieval + ranking)**:

1. **Загрузка и предобработка данных** (`src/data/make_dataset.py`): сырые данные H&M (транзакции, товары `articles`, клиенты `customers`) читаются, очищаются и сохраняются как признаки (`preprocess_and_save_data`, `load_features_data`). Выполняется временнОе разбиение на train/val/test (`time_based_split`).
2. **Построение признаков** (`src/features/build_features.py`): формируются признаки товаров и пользователей, генерируются **BERT-эмбеддинги** по текстовым описаниям товаров (`detail_desc`), а также артефакты для холодного старта.
3. **Обучение модели** (`src/models/train_model.py`, запускается через `train.py`):
   - **Этап retrieval:** по эмбеддингам строится индекс **FAISS** для быстрого поиска похожих товаров;
   - **Этап ranking:** кандидаты от FAISS переранжируются моделью **LightGBM**, гиперпараметры которой подбираются через **Optuna**.
   - Все обученные объекты (модель, FAISS-индекс, эмбеддинги, маппинги, история пользователей) сохраняются как артефакты (`save_artifacts`) в каталог `artifacts/`.
4. **Сервис** (`src/service/api.py`, `src/service/cli.py`): при старте загружает артефакты в память (`load_artifacts`) и отдаёт рекомендации по HTTP. Обучение и сервис разделены: обучение — офлайн-процесс, сервис лишь использует готовые артефакты.



### 6.2. API и endpoints

Реализованы два эндпоинта:

- **`GET /health`** — проверка работоспособности. Возвращает `{"status": "ok", "service": "recsys-api"}`.
- **`POST /recommend`** — основной эндпоинт получения рекомендаций (играет роль `/predict`).

**Параметры запроса `/recommend`:**

| Поле | Тип | Описание |
|------|-----|----------|
| `customer_id` | str (опц.) | ID пользователя, если известен |
| `age` | int (опц.) | Возраст пользователя (0–120) |
| `has_fashion_news` | bool (опц.) | Подписка на новости моды |
| `top_k` | int | Количество рекомендаций (по умолчанию из конфига) |

**Что возвращает:**

| Поле | Описание |
|------|----------|
| `message` | Статус операции |
| `scenario` | Сценарий выдачи: Warm Start / Demographic Cold Start / Global Cold Start |
| `recommendations` | Список ID рекомендованных товаров |
| `latency_ms` | Время обработки запроса в миллисекундах |

Сервис сам выбирает сценарий: если у пользователя есть история — **Warm Start** (FAISS + LightGBM); если известны только демографические данные — **Demographic Cold Start**; иначе — **Global Cold Start**.

### 6.3. Технологический стек

- **API / сервис:** FastAPI, Uvicorn, Typer (CLI), Pydantic.
- **ML / данные:** FAISS (faiss-cpu), LightGBM, Transformers + PyTorch (BERT-эмбеддинги), scikit-learn, Optuna, pandas, numpy.
- **Контейнеризация:** Docker.

**Команды для поднятия сервиса:**

```bash
# сборка образа
docker build -t recsys:latest .

# запуск сервиса
docker run -p 8000:8000 recsys:latest
```

После запуска сервис доступен на `http://127.0.0.1:8000`, Swagger — на `http://127.0.0.1:8000/docs`.

## 7. Наблюдаемость, конфигурация и безопасность

### 7.1. Логи и наблюдаемость

- При старте сервиса в лог пишется адрес запуска и ссылка на Swagger, а Uvicorn логирует события жизненного цикла (`Application startup complete`).
- Ошибки загрузки артефактов перехватываются и выводятся в лог с указанием причины.
- Каждый ответ `/recommend` содержит `latency_ms` — время обработки запроса, что позволяет отслеживать производительность.
- Корректность работы проверяется эндпоинтом `GET /health` и доступностью Swagger-документации.

### 7.2. Конфигурации

Все настраиваемые параметры вынесены в YAML-файлы каталога `configs/` и разделены по назначению на три файла:

- **`config.yaml`** — общие параметры сервиса и данных:
  - `paths`: пути к сырым данным (`raw_data_dir`), обработанным данным (`data_dir`) и артефактам (`artifacts_dir`);
  - `preprocessing`: параметры предобработки — `cutoff_days` (30), `days_for_val/test` (7), `chunk_size` (1 000 000), `price_quantile_bins` (3);
  - `api`: `host` (127.0.0.1), `port` (8000), `default_top_k` (20).
- **`training.yaml`** — параметры обучения:
  - `retrieval.k_candidates` (100) — число кандидатов от FAISS на этапе обучения;
  - `features` — список признаков для LightGBM (`faiss_score`, `faiss_rank`, `price`, `popularity`, `price_diff`);
  - `lightgbm_params` — гиперпараметры модели: `base` (objective `binary`, metric `auc`, `gbdt`, `is_unbalance`, `random_state` 42 и др.), `tuning` (200 раундов, early stopping 20) и `final` (500 раундов, early stopping 30).
- **`inference.yaml`** — параметры выдачи рекомендаций:
  - `retrieval.k_candidates` (150) — число кандидатов на инференсе;
  - `ranking.default_top_k` (20) — размер итоговой выдачи;
  - `cold_start` — значения по умолчанию для холодного старта (`default_age_group` «25-34», `default_news_freq` «NONE»).

Без изменения кода можно перенастроить: пути к данным и артефактам, параметры предобработки, хост/порт и размер выдачи сервиса, число кандидатов retrieval, набор признаков и гиперпараметры LightGBM, а также поведение при холодном старте. В Docker хост переопределяется флагом запуска (`--host 0.0.0.0`), не затрагивая конфиг.

### 7.3. Безопасность

- Секреты (токены, пароли) в коде и конфигах не используются — сервис не требует внешних учётных данных.
- В `.gitignore` исключены виртуальное окружение, кэши и потенциальные `.env`-файлы, чтобы случайно не закоммитить чувствительные данные.
- В `.dockerignore` исключены служебные и временные файлы, чтобы они не попадали в образ.
- Чувствительных персональных данных в репозитории нет; используется обезличенный датасет H&M.

## 8. Ограничения и дальнейшая работа

**Ограничения:**

- **Качество:** ранжирование зависит от качества BERT-эмбеддингов и ограниченного набора признаков; для редких товаров и новых пользователей точность ниже.
- **Скорость:** BERT-эмбеддинги и FAISS-поиск ресурсоёмки; в контейнере модель работает на CPU, что медленнее GPU.
- **Устойчивость:** артефакты загружаются один раз при старте; при их отсутствии сервис стартует, но `/recommend` возвращает ошибку.
- **Объём данных:** пайплайн рассчитан на офлайн-обучение на фиксированном срезе; онлайн-обновления модели нет.

**Что улучшить при наличии времени:**
- *Данные/эксперименты:* добавить датасет с фото, увеличить объём обучающих данных, добавить регулярную валидацию качества, отслеживание метрик (MLflow), A/B-тесты, добавить online-метрики, ежедневное обновление модели.
- *Модель:* добавить модели CV, добавить больше поведенческих признаков, попробовать гибридные модели, расширить подбор гиперпараметров.
- *Сервис:* добавить вывод фото/цены/описание рекомендованных товаров, убрать `reload=True` в продакшене, добавить структурированное логирование и метрики (Prometheus), батч-обработку запросов, кеширование.

**Ключевые сценарии:**

1. **Проверка работоспособности** — запрос к `GET /health`, демонстрация ответа `{"status": "ok"}`.
2. **Получение рекомендаций** — запрос к `POST /recommend` в двух режимах:
   - *Warm Start:* с известным `customer_id` (есть история) — показываем выдачу FAISS + LightGBM;
   *Пример входных данных:* 
   {
     "customer_id": "00000dbacae5abe5e23885899a1fa44253a17956c6d1c3d25f88aa139fdfc657"
   }
   - *Холодный клиент с демографией (Demographic Cold Start)*: без истории, но с известными age и has_fashion_news — выдаём топ-K товаров из соответствующей категории пользователя;
   *Пример входных данных:* 
   {
     "age": 27,
     "has_fashion_news": true,
     "top_k": 20
   }
   - *Полностью холодный клиент (Global Cold Start)*: без customer_id и без демографии — выдаём глобальный топ-K товаров;
   *Пример входных данных:* 
   {
   }
   - В ответе показываем `scenario`, список рекомендаций и `latency_ms`.

**На что обратить внимание преподавателю:**

- **Архитектура:** грамотное разделение retrieval (FAISS) и ranking (LightGBM), офлайн-обучение отдельно от сервиса.
- **Устойчивость:** обработка трёх сценариев (warm / demographic cold / global cold start) без падения сервиса.
- **Удобство API:** понятные эндпоинты, автодокументация Swagger, человекочитаемые входные данные (возраст и подписка вместо «сырых» категорий).
- **Воспроизводимость:** упаковка в Docker, фиксированные зависимости, CPU-сборка для кросс-платформенного запуска.
